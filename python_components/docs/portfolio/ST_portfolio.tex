\section{Outline of the Software Being Tested}
\textbf{RiskBeacon} is a Python-based real-time market risk monitoring system (FastAPI backend + Streamlit dashboard) that ingests OHLCV ticks (\texttt{POST /api/tick}), computes quantitative risk metrics (VPIN, Yang--Zhang volatility, regime classification), persists results to per-ticker CSVs, and generates dashboard-ready Plotly HTML artifacts (\texttt{POST /api/plots/generate}). The system is high-risk because errors can misrepresent market stress; therefore the test process targets quantitative invariants, robustness to malformed data, external dependency failures (Interactive Brokers), and performance under load. Requirements and traceability are documented in \texttt{docs/requirements.md} and \texttt{docs/requirements\_to\_tests.md}.

\section{Learning Outcomes}

\begin{enumerate}
\item \textbf{Analyze requirements to determine appropriate testing strategies} \marginpar{[default 20\%]}
\begin{enumerate}
\item \textbf{Range of requirements, functional requirements, measurable quality attributes, qualitative requirements}\\
\textbf{Range:} I defined 17 testable requirements (\texttt{RB-REQ-01..RB-REQ-17}) spanning functional correctness (tick persistence, plot generation), quantitative invariants (VPIN in $[0,1]$, volatility $\ge 0$), robustness (bad CSV lines, missing sentiment, IB failure), performance targets (latency/time), and MLOps reproducibility (MLflow artifacts). Evidence: \texttt{docs/requirements.md}.

\item \textbf{Level of requirements, system, integration, unit}\\
\textbf{Levels:} requirements explicitly span unit (RB-REQ-06/07/09), integration (RB-REQ-02/13), and system (RB-REQ-01/03/04/05/14/15/16/17). Evidence: \texttt{docs/requirements.md} (each requirement includes a level) and traceability: \texttt{docs/requirements\_to\_tests.md}.

\item \textbf{Identifying test approach for chosen attributes}\\
\textbf{Testing philosophy (lecture-aligned):}
\begin{itemize}
  \item \textbf{Verification vs validation:} verification is requirements-driven tests + automated checks (pytest, GX, MLflow, perf). Validation is whether the Streamlit dashboard supports risk monitoring decisions (manual scenario checks + stable/fast UX).
  \item \textbf{Optimistic vs pessimistic inaccuracy:} optimistic testing can miss faults; mitigated via redundancy (unit + property + integration + perf + CI). Pessimistic analysis may reject correct artifacts due to approximation/tool limits (GX version differences); mitigated via restriction and documentation.
  \item \textbf{A\&T principles (repo examples):}
  \begin{itemize}
    \item \textbf{Sensitivity:} deterministic unit tests for services (\texttt{test/unit\_testing/service\_modules/*}).
    \item \textbf{Redundancy:} VPIN/vol checked by invariants (Hypothesis) + data validation (GX) + integration/perf.
    \item \textbf{Restriction:} disable heavy FinBERT download in CI with \texttt{RISKBEACON\_DISABLE\_FINBERT=true} (\texttt{.github/workflows/ci.yml} as \$env variable).
    \item \textbf{Partition:} category-partitioning for \texttt{/api/tick} inputs (see LO3) + boundary cases in tests.
    \item \textbf{Visibility:} CI artifacts (coverage XML/HTML, exported GX suites) and perf prints.
    \item \textbf{Feedback:} defects (plot crash, VPIN saturation, CI/GX brittleness) drove new tests and instrumentation (commits \texttt{0d5997f}, \texttt{c1cae2d}, \texttt{ed7f133}).
  \end{itemize}
\end{itemize}

\item \textbf{Assess the appropriateness of your chosen testing approach}\\
\textbf{Appropriateness:} approaches match the risk profile: invariants for oracle-free quant correctness, integration tests for API/CSV side-effects, perf tests for latency targets, and CI automation for repeatability and visibility. Known limitations (IB permissions/market hours; toolchain constraints for GX on Windows without pinning) are documented and mitigated via fallbacks (\texttt{ib\_troubleshoot.py}, pinned \texttt{requirements-dev.txt}).
\end{enumerate}
\item \textbf{Design and implement comprehensive test plans with instrumented code} \marginpar{[default 20\%]}
\begin{enumerate}
\item \textbf{Construction of the test plan}\\
\textbf{Auditable plan:} \texttt{docs/PLAN.md} defines scope, a test inventory table (tests $\rightarrow$ files $\rightarrow$ RB-REQs), a risk register (IB, malformed CSVs, heavy deps), and monitoring metrics (coverage trend, CI pass rate, perf med/p95).

\item \textbf{Evaluation of the quality of the test plan}\\
\textbf{Quality assessment:} the plan prioritises the critical path (ingestion $\rightarrow$ persistence $\rightarrow$ plots) early to maximise leverage (fault cost grows with time). Residual gaps are explicitly stated (metamorphic ML tests and time-series split/backtesting extensions), preventing over-claiming adequacy.

\item \textbf{Instrumentation of the code}\\
\textbf{Instrumentation (testability changes):} robust logging and controllable behaviour were added to make failures diagnosable and tests stable: plot loader deduplication (\texttt{services/plotService.py}), fast rolling volatility cache (\texttt{services/vol\_service.py}), CI-safe sentiment flag 
\newline(\texttt{services/sentimentService.py}), and IB status endpoints + local troubleshoot tool (\texttt{ib\_troubleshoot.py}).

\item \textbf{Evaluation of the instrumentation}\\
\textbf{Evaluation:} instrumentation improves visibility and feedback loops (CI artifacts, logs, and deterministic harnesses). External dependency variability (IB) remains a limitation, mitigated by graceful degradation and explicit diagnostics.
\end{enumerate}

\item\textbf{Evaluation criteria for the adequacy of the testing}\\
\textbf{Adequacy criteria (lecture-aligned):} coverage (statement/branch proxy via pytest-cov) and requirement traceability (RB-REQ $\rightarrow$ tests). Yield assessment via mutation testing (\texttt{mutmut}) is \textbf{attempted} on high-risk quant services (\texttt{services/vpin\_service.py}, \texttt{services/vol\_service.py}) via \texttt{.github/workflows/mutation.yml}, but faces challenges with dependency isolation in the mutmut sandbox (import resolution, pytest configuration conflicts). This limitation is documented in \texttt{docs/mutation\_testing.md} and demonstrates understanding of mutation testing concepts even if full automation is not achieved.

\\textbf{Results evidence:} local execution produced \textbf{200 passed, 3 skipped, 4 xfailed} tests; CI produces similar results and uploads auditable artifacts (coverage + GX suites). GX is skipped on some Windows setups when GE runtime cannot construct an ephemeral validator; CI remains the audited source for exported GX suites. \textbf{xfailed} tests are deliberate, non-breaking evidence of discovered imperfections / future requirements (e.g., plot filename/endpoint mismatch) captured as executable checks. Coverage output (\texttt{coverage.xml}, \texttt{htmlcov/}), perf test prints (median/p95, elapsed time), and CI artefact uploads (\texttt{.github/workflows/ci.yml}) provide reproducible evidence. Data validation produces suite exports (human-readable JSON + summary). \textbf{Backtesting evidence:} strategy backtesting on AMD/NVDA/TSLA portfolio (2023-12 to 2025-11) demonstrates out-of-sample reliability: test period (2025-04 to 2025-11) achieved 11.15\% return with Sharpe 0.82, validating strategy robustness despite full-period challenges. Evidence: \texttt{test/backtesting/research.ipynb} with reproducible train/test splits, sentiment filters, and risk management (stop-loss, fees).


\item \textbf{Evaluation of the results}\\
\textbf{Evaluation:} coverage is treated as an adequacy criterion (not a proof). Uncovered/low-coverage modules are justified when they depend on external artifacts (\texttt{services/data\_replay\_service.py}) or optional integrations (IB). Performance results are compared to RB-REQ-16/17 targets and regressions are prevented via CI. \textbf{Backtesting evaluation:} the strategy demonstrates sound methodology (train/test split, fees included, no look-ahead bias) with defensible results for coursework. Test period performance (11.15\% return, Sharpe 0.82) validates out-of-sample reliability, while full-period challenges (-4.93\%) demonstrate honest reporting of limitations. The backtesting process validates RB-REQ-11 (time-series split enforcement) and provides evidence of strategy reliability assessment.
\end{enumerate}

\item \textbf{Construct an appropriate CI pipeline for the software}\\
\textbf{CI pipeline:} GitHub Actions workflow \texttt{.github/workflows/ci.yml} runs pytest with coverage and exports GX suite documentation. It uploads \texttt{coverage.xml}, \texttt{htmlcov/}, and \texttt{docs/data\_validation/gx\_suites/}.

\item\textbf{Automate some aspects of the testing}\\
\textbf{Automation strategy (lecture-aligned):} automate repetitive execution and measurement (unit/integration/perf measurement, coverage, suite exports) while restricting heavy/optional dependencies (FinBERT disabled in CI via env flag; IB not required). This maximises cost-effectiveness and visibility.
